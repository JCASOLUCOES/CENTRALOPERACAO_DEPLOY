Como resolver esse problema?

Lógica de atendimento e resolução de incidentes no CRM Actyon

Versão 1.0 Suporte JCA

Lógica clara e padronizada para atender e resolver incidentes no CRM Actyon, garantindo classificação correta, diagnóstico eficiente, comunicação transparente e rastreabilidade das ações.

Índice clique para abrir a seção

1

Classificação do Incidente (Prioridade e Urgência)

Todo atendimento começa pela definição de impacto e prioridade — vale para qualquer incidente: falhas no CRM, lentidão, indisponibilidade, erros de rede, falha IIS ↔ SQL ou erros de API.

Perguntas iniciais

  • Quantos usuários afetados? 1 usuário → baixo impacto; equipe inteira ou operação parada → alto impacto.
  • O sistema está indisponível ou só lento? Indisponível → crítico; degradação parcial → moderado.
  • Existe prazo operacional sensível? Ex.: fechamento, envio de arquivos, call center ativo.

Resultado esperado

  • P1 = CRM ou operação parada
  • P2 = Lentidão / falhas parciais
  • P3 = Erros pontuais / dúvidas / comportamento isolado

Uma boa classificação define a urgência, orienta o esforço da equipe e a comunicação com o cliente, evitando retrabalho.

2

Diagnóstico Inicial (Checklist de 60 segundos)

Objetivo: identificar rápido se o problema é local, geral ou de infraestrutura, sem perder tempo em testes irrelevantes.

O problema é local ou geral?

  • Testar com outro usuário e em outro computador.
  • Testar a API diretamente pela URL base.
  • Interpretação: se apenas um usuário é afetado, o problema é local (máquina, perfil, permissão, navegador, rede local).

Estado dos serviços principais

  • API do CRM Actyon online?
  • IIS respondendo?
  • SQL Server acessível?

Testes rápidos: login no CRM, endpoint público simples (ex.: /api/health) e, no servidor, verificar se o application pool do site está rodando.

Comunicação entre servidores (IIS ↔ SQL)

  • O IIS consegue pingar o servidor SQL?
  • A porta 1433 está liberada?
  • A conexão está autenticando corretamente?
  • Algum serviço (IIS ou SQL) reiniciou recentemente?
  • Há lentidão só em consultas ao banco, e não na aplicação inteira?

Causas mais comuns em erros 500, de autenticação ou timeouts: latência de rede, application pool travado, SQL lento com alta espera e execuções pesadas consumindo recursos.

3

Consulta a Documentos e Histórico

Após a triagem rápida, consulte a documentação e o histórico de atendimentos.

Verificações necessárias

  • POPs relacionados ao tipo de incidente.
  • Chamados anteriores com o mesmo erro ou mensagem.
  • Orientação formal de atendimento já existente.
  • Solução rápida já validada para o problema.

Isso evita redescobrir problemas conhecidos, padroniza o atendimento e mantém aderência aos procedimentos oficiais. Sem POP para o caso, registre a solução adotada para embasar a criação futura do documento.

4

Execução do Plano de Ação

Com base na causa provável, execute ações de correção. As listadas abaixo resolvem a maior parte dos casos.

Ações gerais de infraestrutura

  • Reiniciar o application pool específico (sem reiniciar todo o site).
  • Verificar e corrigir credenciais de comunicação (banco, APIs etc.).
  • Ajustar configuração de rede / rota / DNS, quando aplicável.
  • Encerrar sessões zumbis no SQL com cuidado e, preferencialmente, com orientação do time técnico.
  • Confirmar que o servidor IIS não está saturado (CPU, memória, disco).
  • Verificar tarefas de carga ou rotinas que estejam travando o ambiente.

Casos de erro de API ou aplicação

  • Verificar o arquivo de configuração (ex.: appsettings).
  • Testar o endpoint isolado, fora do CRM, quando possível.
  • Verificar exceções registradas nos logs do CRM.
  • Validar se o banco está acessível para a aplicação em execução.
5

Comunicação com o Cliente

A comunicação deve ser clara, objetiva e contínua.

Boas práticas

  • Informar ao cliente o que já foi verificado.
  • Deixar claro que o atendimento segue o POP ou procedimento oficial.
  • Alinhar prazo realista com base na prioridade (P1, P2, P3).
  • Registrar todas as interações e passos no CRM Actyon.

Isso reduz ruídos, aumenta a confiança do cliente e gera histórico útil para casos futuros.

Estrutura sugerida para atualizações

  • Status atual: o que já foi feito.
  • Próximo passo: o que está sendo verificado agora.
  • Prazo: quando haverá nova posição ou conclusão estimada.
  • Registro: síntese lançada no CRM Actyon para rastreabilidade.
6

Fechamento do Incidente

Documentação e categorização

  • Documentar a causa raiz (quando identificada) e todas as ações realizadas, inclusive as que não deram certo.
  • Categorizar corretamente: rede, banco de dados, aplicação, ambiente/infraestrutura, usuário/permissão, credenciais/autenticação ou operação/processo.

Ações preventivas futuras

  • Ajuste de capacidade (servidor, banco, rede).
  • Revisão de configuração de ambiente.
  • Melhoria ou criação de POP.
  • Treinamento adicional para usuário ou equipe interna.

Um bom fechamento evita recorrência e melhora a qualidade dos próximos atendimentos.

7

Fluxo Resumido (Visão de Suporte JCA)

Use este fluxo como checklist rápido em qualquer incidente.
  • Classificar impacto (P1 / P2 / P3).
  • Checar se é problema geral ou isolado.
  • Testar infraestrutura: IIS, API, SQL, rede.
  • Consultar POPs e histórico de incidentes semelhantes.
  • Executar ações rápidas e validadas.
  • Atualizar CRM e comunicar o cliente.
  • Registrar solução e causa raiz.
8

Exemplos Práticos de Lógica Aplicada

Caso: Lentidão no CRM

  • Classificar impacto: normalmente P2 (lentidão, sem parada total).
  • Verificar se é geral (vários usuários/módulos) ou específico.
  • Testar endpoint de saúde (ex.: /api/health).
  • Verificar consumo de recursos no IIS (CPU, memória, filas de requisição).
  • Checar waits do SQL (sem ferramentas externas avançadas).
  • Registrar ações e comunicar o cliente sobre o andamento.

Caso: Erro 500 para todos os usuários

  • Classificar imediatamente como P1 (indisponibilidade geral).
  • Checar o application pool do IIS (estado, reciclagem, logs de erro).
  • Verificar comunicação IIS ↔ SQL (ping, porta 1433, autenticação).
  • Conferir logs do CRM por erros críticos ou exceções recentes.
  • Corrigir o problema ou escalar para o time responsável (desenvolvimento/infra).
  • Manter o cliente atualizado via CRM Actyon até a normalização.

Caso: Usuário não consegue acessar

  • Verificar se o login funciona para outro usuário (descartar problema geral).
  • Testar em navegador anônimo ou outra máquina para isolar cache/ambiente local.
  • Checar permissões do usuário no CRM (perfis, grupos, regras de acesso).
  • Verificar expiração de senha ou bloqueio de usuário.
  • Registrar no CRM e comunicar o cliente sobre causa e solução.
