Como Funcionam os Servidores e a Comunicação – Explicação para Leigos

Metáfora do Restaurante

Imagine que o CRM Actyon funciona como um restaurante:

  • O IIS é a cozinha, onde os pedidos são recebidos e preparados (a aplicação funciona aqui).
  • O Banco de Dados (SQL) é a despensa, onde ficam todos os ingredientes (dados dos clientes, títulos, atendimentos etc.).
  • A rede é o corredor que liga a cozinha à despensa.

Para o sistema funcionar, a cozinha precisa conseguir ir até a despensa buscar informações o tempo todo.

O que isso significa na prática

Agora, dependendo do cliente, a cozinha e a despensa podem estar em locais diferentes. Isso impacta diretamente a estabilidade e a velocidade do sistema.

Como Identificar Onde Está o Problema (Explicação para Leigos)

Abaixo está um guia simples para diagnosticar onde está o problema, mesmo sem conhecimento técnico.

1. Se o sistema nem abre ou trava no login

Provável problema: Internet do cliente fraca ou caindo; servidor IIS fora do ar; firewall do cliente bloqueando o acesso.

Como testar: Testar abrir outro site; testar outro computador; verificar se todos estão com o mesmo problema.

Se todos estão com o problema → o erro está no servidor.

2. Se o sistema abre, mas fica lento

Provável problema: Lentidão entre o IIS e o Banco de Dados; internet oscilando (em ambientes híbridos); banco de dados sobrecarregado.

Como testar: Ver se a internet está estável; perguntar se vários usuários também percebem lentidão; perguntar se o cliente está em horário de pico.

Lentidão generalizada → geralmente o SQL está lento.

3. Se apenas uma tela específica não carrega

Provável problema: Falta de permissão; erro em algum dado específico; API retornando erro apenas naquele módulo.

Como testar: Pedir para outro usuário abrir a mesma tela; testar em outra máquina; testar um registro diferente.

Se só acontecer com um usuário → é permissão. Se só com um registro → é dado inconsistente.

4. Se o sistema trava de tempos em tempos

Provável problema: Instabilidade da comunicação entre IIS e SQL; internet do cliente oscilando.

Como testar: Ver se ocorre sempre no mesmo horário; ver se a internet do cliente está oscilando; ver se o servidor está com CPU alta.

Travas cíclicas → geralmente é o App Pool ou SQL com sessões presas. Considere reiniciar o IIS para avaliar melhora.

5. Se o sistema fica lento ou trava em horários aleatórios

Provável problema: Disco do servidor IIS ou SQL com pouco espaço; disco com escrita/leituras lentas (I/O alto); log do SQL crescendo sem controle (LOG.LDF gigante); backup rodando em horário comercial; antivírus escaneando pastas críticas; fragmentação alta do disco (em HDD).

Como testar: Verificar espaço livre no disco do servidor (C: e partição do SQL); verificar no Gerenciador de Tarefas o disco em 100%; checar backups/cópias/relatórios no horário; checar o tamanho do LOG.LDF; verificar se o antivírus analisa arquivos do IIS ou MDF/LDF; rodar CrystalDiskInfo/perfmon.

Disco lotado → SQL e IIS perdem performance imediatamente. Disco com I/O alto → telas lentas, travamentos e timeouts.

6. Se o servidor fica lento apenas em alguns momentos do dia

Provável problema: Servidor SQL com pouca memória disponível; CPU constante acima de 80% (IIS ou SQL); App Pool reciclando em horário crítico; serviços externos consumindo recursos; manutenção do Windows em horário comercial.

Como testar: Ver uso de CPU e memória no Gerenciador de Tarefas; ver histórico do SQL em horários de pico (Activity Monitor); consultar o agendamento de Reciclagem do App Pool; identificar processos que usam memória excessiva; verificar se há Windows Update ou serviços agendados.

CPU alta ou memória cheia → lentidão geral. App Pool reiniciando → usuários desconectados e telas travam.

Cenários de Infraestrutura – Onde Ficam Cozinha e Despensa

1. Cenário: IIS na nuvem + Banco local (híbrido)

A cozinha (IIS) fica na internet.
A despensa (SQL) fica dentro da empresa do cliente.
O corredor é a internet.

  • 👉 Se a internet do cliente cai ou fica lenta, o sistema trava.
  • 👉 Se o firewall do cliente bloqueia a porta, a cozinha não consegue buscar dados.

2. Cenário: Tudo local (IIS + SQL dentro da empresa)

Cozinha e despensa estão no mesmo prédio.
O corredor é a rede interna (LAN).

  • 👉 Se algum cabo, switch ou servidor local estiver lento, o sistema fica lento.
  • 👉 Se a máquina do IIS cair, ninguém consegue usar o sistema.

3. Cenário: Tudo na nuvem

Cozinha e despensa ficam no mesmo datacenter na internet.
O corredor é interno e ultrarrápido.

  • 👉 Mais estável
  • 👉 Menos chance de travar
  • 👉 Só depende da internet do cliente para acessar o sistema

Dicas Simples para o Suporte Diagnosticar Rápido

Perguntas-chave para diagnóstico rápido

  • Pergunte se o problema é geral
    → Se todo mundo está com o problema, é o servidor.
  • Pergunte se a internet está estável
    → Em ambientes híbridos, é o principal culpado.
  • Veja se outra máquina faz o mesmo erro
    → Se não fizer, o problema é local da máquina do usuário.
  • Teste comunicação IIS → SQL
    → Quando essa comunicação falha, o sistema cai ou trava.
  • Verifique espaço em disco e uso de CPU/Memória
    → Disco cheio ou recursos esgotados causam lentidão imediata.
  • Antes de reiniciar qualquer coisa, verifique logs
    → Muitas vezes o log já mostra exatamente o erro.

Comandos Rápidos de Diagnóstico

Comandos executados no CMD/PowerShell para validar cada camada em poucos minutos. Adapte os endereços (IPs, nomes, portas) para o ambiente do cliente.

5.1. Identidade da máquina e rede

ipconfig /all          :: IP, máscara, gateway e DNS da estação
hostname               :: nome do computador
whoami                 :: usuário logado

5.2. Comunicação com o destino (rede/internet)

ping 8.8.8.8 -t        :: conectividade + perda de pacotes (CTRL+C para parar)
ping SERV_CLIENTE      :: destino por nome (resolução DNS)
tracert SERV_CLIENTE   :: rota até o destino, salto a salto
pathping SERV_CLIENTE  :: perda de pacotes por salto (mais lento, mais completo)
nslookup www.actyon.com.br :: conferir resolução de DNS

5.3. Portas e serviços (IIS, SQL, API)

netstat -ano | findstr :443     :: porta 443 (HTTPS/IIS) em escuta?
netstat -ano | findstr :1433    :: porta do SQL Server em escuta?
netstat -ano | findstr :8080    :: porta de API/back em escuta?

:: PowerShell (testa conectividade de porta como um telnet)
Test-NetConnection SERV_CLIENTE -Port 1433
Test-NetConnection API_JCA -Port 443

5.4. Serviços críticos (rodando no servidor)

services.msc           :: abrir console de serviços
:: Serviços a conferir:
::   - World Wide Web Publishing Service (W3SVC) -> IIS
::   - SQL Server (MSSQLSERVER)                   -> banco
::   - SQL Server Agent                           -> jobs agendados

:: Alternativa via PowerShell:
Get-Service W3SVC, MSSQLSERVER | Select-Object Name, Status

5.5. Recursos do servidor e logs

:: Espaço em disco (no CMD)
wmic logicaldisk get caption, freespace, size

:: Uso de CPU/memória em tempo real
taskmgr

:: Eventos recentes de erro (PowerShell)
Get-EventLog -LogName System -Newest 20 | Where-Object { $_.EntryType -eq 'Error' }
Get-EventLog -LogName Application -Newest 20 | Where-Object { $_.EntryType -eq 'Error' }

:: IIS: reiniciar App Pool sem reiniciar o servidor
iisreset /stop
iisreset /start

5.6. Interpretação rápida dos resultados

  • ping com perda de pacotes → instabilidade de rede ou internet.
  • tracert parando no mesmo salto → o problema está naquele ponto da rota (roteador, firewall, operadora).
  • nslookup sem resposta → problema de DNS (resolução de nomes).
  • porta não escutando → serviço parado ou firewall bloqueando.
  • porta escutando, mas sistema não conecta → firewall intermediário, string de conexão ou VPN.
  • W3SVC/MSSQLSERVER parados → causa direta da indisponibilidade.
  • Eventos de erro com hora exata → cruzar com o horário reportado pelo cliente.
