Manual de Boas Práticas de Rede e API

Diagnóstico e resolução de problemas de rede, API e conectividade no CRM Actyon.

Versão: 1.0 Suporte / Infraestrutura / Desenvolvimento 13 seções

Estabelecer boas práticas, padrões de conduta e orientações técnicas para diagnóstico e resolução de problemas de rede, API e conectividade no CRM Actyon, garantindo rastreabilidade, eficiência e qualidade no atendimento.

Objetivo do Manual

Finalidade

Este manual serve como referência oficial para o time da JCA na análise de problemas de rede, lentidão e falhas no CRM Actyon, além de erros de integração via API (marketplaces, parceiros etc.).

Público-alvo

A ideia é que qualquer analista, mesmo menos experiente, consiga:

  • Seguir um passo a passo claro;
  • Entender onde está o problema (cliente, internet, rede interna, firewall, IIS, SQL, API externa);
  • Registrar corretamente as evidências no chamado.

Uso recomendado

Sempre que possível, use este manual do começo ao fim do fluxo antes de escalar.

1

Visão Geral do Ambiente Actyon

1.1 Fluxo de Comunicação

Fluxo básico:

WEB: Usuário / Sistema Externo → Internet → Firewall / Rede Interna → IIS (API Actyon) → SQL Server
COB: Usuário / Sistema Externo → Internet → Firewall / Rede Interna → SQL Server (CONEXÃO LOCAL)
  • Quando há integração externa: Actyon (IIS) → Internet → API do Parceiro

1.2 Possíveis Pontos de Falha

  • API / IIS / Actyon
  • Comunicação IIS ↔ SQL Server
  • Rede interna (cliente ou JCA)
  • Internet / rota até APIs externas
  • SQL Server (performance)
  • Configuração da API (status HTTP / regras de negócio)

1.3 Fluxo Padrão de Diagnóstico JCA

  • 0. Testar máquina local ↔ SQL (ActyonCOB)
  • 1. Testar API internamente (no servidor)
  • 2. Testar comunicação IIS ↔ SQL
  • 3. Checar rede interna / DNS / firewall
  • 4. Checar internet do cliente
  • 5. Validar API externa POSTMAN (status HTTP e corpo de resposta)
  • 6. Verificar SQL (performance) se necessário
2

Princípios Gerais de Atendimento

2.1 Separar Rede de Aplicação

  • Se você recebe um código HTTP (200-499), a rede em geral está funcionando; o problema tende a ser formato de requisição, autenticação, regra de negócio ou erro interno da aplicação.
  • Se você não recebe nada (timeout / conexão expirou) ou erro HTTP (500), é necessário investigar rede, firewall, DNS, rota ou indisponibilidade total do serviço.

2.2 Registrar Evidências

Sempre registrar no chamado (se possível):

  • Print ou texto completo do erro
  • Data e hora aproximadas
  • URL chamada (endpoint completo)
  • Método HTTP (GET / POST / PUT / DELETE)
  • Corpo da requisição (quando for API)
  • Código HTTP retornado (quando houver)

2.3 Comparar Cenários

  • Funciona em um computador e não em outro?
  • Funciona via 4G e não via rede corporativa?
  • Funciona localmente no servidor, mas não de fora?
  • Comparar cenários ajuda a isolar onde está o problema.
3

Camada API / IIS – O Actyon está Respondendo?

3.1 Testes Básicos no Servidor IIS

Objetivo: saber se o backend está OK antes de culpar rede externa.

  • No servidor IIS:
  • Testar via navegador: http://localhost/swagger (se existir)
  • Testar via Postman no próprio IIS usando os mesmos endpoints, métodos, headers e body que o cliente utiliza

3.2 Interpretação

  • Se localmente responde rápido e estável: provável problema fora do servidor (rede do cliente, internet, firewall/rota).
  • Se localmente já está lento ou com erro: problema no próprio Actyon / IIS, na comunicação com SQL ou no SQL / regras de negócio.
4

Camada IIS ↔ SQL Server – Comunicação Entre Servidores

A comunicação entre IIS e SQL é crítica para o Actyon. Instabilidade aqui aumenta muito o tempo de resposta da API.

4.1 Testes de Conectividade

Ping interno (latência e perda):

ping 192.168.2.154 -t
  • 0–1 ms → ideal
  • > 5 ms → pode gerar lentidão perceptível
  • Perda de pacotes → problema de rede interna (switch, cabo, VLAN, firewall)
  • Teste da porta do SQL (padrão 1433): telnet SQLSERVER 1433
  • Conectou → porta acessível
  • Não conectou → firewall bloqueando, porta alterada ou serviço SQL parado
  • Rota interna (tracert): tracert SQLSERVER
  • Ideal: 1 ou 2 hops
  • Muitos hops → rede interna mal segmentada (VLAN/switch/roteamento)

4.2 Análise de Conexões no IIS

netstat -ano | findstr 1433
  • Observar:
  • Muitas conexões em SYN_SENT → algo está filtrando ou bloqueando (firewall, rede instável)
  • Muito TIME_WAIT → muitas reconexões, pode indicar quedas frequentes
  • Poucas conexões ativas → verificar se a aplicação está reconectando demais

4.3 Verificações Diretas no SQL Server

SELECT client_net_address, connect_time
FROM sys.dm_exec_connections
WHERE session_id > 50;
  • Verificar:
  • Se o IIS aparece como origem
  • Se há muitas reconexões em curto período (quedas)
Erro FIREDAC entre ActyonCOB e SQL: quando o cliente apresenta erro FIREDAC ao tentar conectar do ActyonCOB ao SQL, significa que aquela máquina específica não está conseguindo estabelecer conexão com o SQL. Analise da estação com erro: teste ping e porta 1433 (telnet) para o servidor SQL, confirme a rede/VPN, verifique firewall local (Windows Defender, antivírus) e a string de conexão. Se as demais máquinas conectam normalmente, é forte indício de problema local na estação.
5

Rede Interna (JSA e Cliente)

5.1 Testes Básicos

  • No computador do usuário ou no servidor, usar:
  • ping → latência e perda de pacotes
  • pathping → perda de pacotes por salto
  • tracert → rota até o destino (IIS, SQL, API externa)
  • Observar: latência muito variável, perda de pacotes em qualquer salto, rotas com muitos hops

5.2 Comparação de Estações e Redes

  • Em outra máquina da mesma rede o problema existe?
  • Em outra rede (4G, outra operadora) o problema some?
  • Se testar direto do servidor para fora, está normal?
  • Isso ajuda a saber se o problema é restrito a uma estação, a uma sub-rede/VLAN, ao link de internet ou ao firewall.
6

Firewall e Portas Críticas

Problemas frequentes: bloqueios parciais ou inspeção excessiva.

6.1 Pontos Críticos (verificação geralmente cabe à empresa que cuida do servidor)

  • Regras liberando apenas porta, mas não o origem/destino corretos
  • Inspeção profunda (DPI) em tráfego interno IIS ↔ SQL
  • SSL inspection quebrando comunicação HTTPS com APIs externas
  • Logs mostrando quedas intermitentes do mesmo IP/porta

6.2 Portas Mais Visadas e Recomendações (Internet)

  • 22 (SSH): acesso remoto seguro. Usar chave pública, limitar IPs, idealmente via VPN.
  • 23 (Telnet): acesso remoto não seguro. Evitar uso e nunca expor na internet.
  • 25 (SMTP): envio de e-mails. Cuidado com relay aberto e spam.
  • 53 (DNS): resolução de nomes. Cuidado com spoofing e DDoS de amplificação.
  • 80 (HTTP): navegação web. Usar HTTPS sempre que possível.
  • 443 (HTTPS): navegação segura. Manter protocolos e cifras atualizados.
  • 445 (SMB): compartilhamento de arquivos. Nunca expor na internet (riscos como EternalBlue/WannaCry).
  • 3389 (RDP): acesso remoto a desktops Windows. Usar VPN, MFA e restringir IPs.
  • Regra de ouro: tudo que for acesso remoto (SSH, RDP, SMB) não deve estar exposto diretamente na internet. Usar VPN ou túnel seguro.
7

Internet / Rota Externa até a JSA ou APIs

7.1 Testes Recomendados

A partir do cliente:

  • ping para o host externo (JSA ou API do parceiro)
  • tracert para o mesmo host
  • pathping para avaliar perda de pacotes
  • Testar a mesma URL de outra rede (4G) e/ou outro computador

7.2 Interpretação

  • Se apenas a rede corporativa falha, mas 4G funciona: problema no firewall/roteador/regras de saída do cliente
  • Se há perda de pacotes ou latência alta já no provedor: orientar o cliente a abrir chamado com a operadora
  • Se todos têm problema para o mesmo endpoint: possível instabilidade do parceiro ou da própria JSA
8

Status HTTP – Interpretação na Prática

Lembrar: 2xx → sucesso; 4xx → erro na requisição do cliente; 5xx → erro no servidor (lado API).

8.1 Tabela de Referência (Resumida)

  • 200 (OK): requisição processada com sucesso
  • 201 (Created): recurso criado com sucesso
  • 204 (No Content): ação concluída sem conteúdo na resposta
  • 400 (Bad Request): JSON mal formado, campo obrigatório ausente ou formato inválido
  • 401 (Unauthorized): autenticação inválida (token/usuário/senha)
  • 403 (Forbidden): autenticado, mas sem permissão ao recurso
  • 404 (Not Found): recurso não existe na API (endpoint/pedido etc.)
  • 406 (Not Acceptable): header Accept pedindo formato não suportado
  • 415 (Unsupported Media Type): Content-Type incorreto (usar application/json; charset=UTF-8)
  • 422 (Unprocessable Entity): viola regra de negócio, mesmo com formato correto
  • 429 (Too Many Requests): limite de requisições excedido (rate limit)
  • 500/502 (Internal Server Error): erro interno no servidor da API
  • 503 (Service Unavailable): API temporariamente indisponível/manutenção
  • 504 (Gateway Timeout): servidor da API demorou demais para responder
Quando o Problema NÃO é Rede: se você recebe qualquer 2xx ou 4xx, a requisição chegou na API (DNS, rota, firewall básico e internet estão funcionando). O foco passa a ser: corpo da requisição (JSON, campos, tipos), autenticação, regras de negócio e possíveis erros internos do parceiro (5xx).

8.3 Corpo de Erro (JSON)

Sempre registrar no chamado:

  • JSON de erro retornado
  • Endpoint
  • Método
  • Headers principais (Authorization, Content-Type, Accept)
  • Body enviado
9

SQL Server – Quando Parece Rede, mas é Banco

Muitos relatos de "rede lenta" são, na verdade, problemas de SQL.

9.1 Indicadores

  • WAITs altos (PAGEIOLATCH, ASYNC_NETWORK_IO, LCK_*)
  • CPU alta no servidor SQL
  • Índices muito fragmentados
  • Consultas demoradas
  • Deadlocks frequentes
  • TempDB sobrecarregada

9.2 Ferramentas

  • sp_whoisactive para ver sessões, waits e consultas em execução
  • SQL Profiler / Extended Events para rastrear queries problemáticas
  • DMVs (sys.dm_exec_query_stats, sys.dm_db_index_physical_stats etc.)
  • Se o SQL está sobrecarregado, a API vai responder mais lenta e pode estourar timeout em algumas requisições, mesmo que a rede esteja perfeita.

Checklists de Uso Diário

10.1 Checklist Rápido (Nível 1)

  • O que o usuário sente? (lento, não abre, erro específico, horário em que acontece)
  • Sistema local ou integração externa?
  • Tem código de erro? (print, status HTTP, mensagem)
  • Testar acesso básico no cliente (outros sites)
  • Registrar tudo no chamado (data/hora, usuário, estação/IP, prints)

10.2 Checklist Estendido – Problema no Actyon

  • Testar os servidores IIS (health, swagger, Postman local)
  • Se local está OK → focar na rede do cliente (ping, tracert, pathping, comparação)
  • Se local está lento → focar em IIS ↔ SQL (ping, telnet, tracert, netstat) e depois SQL (waits, CPU, consultas)

10.3 Checklist – Problema em Integração Externa

  • Fazer requisição de teste via Postman com credenciais e payload reais
  • Se não houver resposta (timeout): testar ping/path para host da API e outra rede (4G)
  • Se houver resposta com status HTTP: usar a tabela de status (4xx = requisição; 5xx = parceiro)
  • Registrar endpoint, método, headers, body, código HTTP e corpo de resposta

Exemplos Rápidos

Caso 1 – Actyon lento para todos

Testar health local → se lento, olhar IIS ↔ SQL e depois o banco.

Caso 2 – Integração com marketplace retorna 504

Testar Postman, rota e, se tudo normal, provável problema no parceiro.

Caso 3 – Erro 401 em integração

Revisar credenciais, token, headers e permissões no painel do parceiro.

Caso 4 – Usuários caindo o tempo todo

Executar ping -t do cliente para o servidor, pathping e verificar se é geral ou só em uma estação.

12

Boas Práticas Preventivas

  • Monitorar latência IIS ↔ SQL e CPU/memória de IIS e SQL
  • Documentar IPs, nomes, portas e URLs de APIs externas
  • Não expor RDP/SSH/SMB diretamente; usar VPN e MFA
  • Manter SO, IIS, SQL e firewall atualizados
  • Manter padrão de logs com data/hora, usuário, estação, códigos de erro, prints e JSONs
